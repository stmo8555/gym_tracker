# JPA annotations: are they needed, what do they do, how do they compare

## Are JPA annotations "needed"?

Only if you want an ORM (Hibernate) to manage persistence for you. An
annotation-mapped class (`@Entity`) lets you write `repo.save(workout)` and
`repo.findAll()` and never touch SQL — Hibernate generates the
`INSERT`/`SELECT`/`UPDATE` for you based on what the annotations declare.

`householdPlanner` makes the opposite choice entirely: no ORM, no
annotations, no generated SQL — every query is hand-written and every row is
manually `Scan()`'d into a plain struct. Both are legitimate; JPA trades
control for less boilerplate, `pgx` trades boilerplate for full control over
every query. Neither is "more correct."

## What each one does, mapped to `V1__init.sql`

Take `Workout.java` next to the `workouts` table:

```sql
CREATE TABLE workouts (
    id INT GENERATED by DEFAULT AS IDENTITY PRIMARY KEY,
    name TEXT NOT NULL,
    user_id INT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    program_id INT NULL REFERENCES programs(id)
);
```

```java
@Entity                                    // "this class maps to a table"
@Table(name = "workouts")                  // which table — omit it and Hibernate guesses from the class name
public class Workout {

    @Id                                    // this field is the PRIMARY KEY
    @GeneratedValue(strategy = GenerationType.IDENTITY)  // matches "GENERATED BY DEFAULT AS IDENTITY"
    private Integer id;

    @Column(nullable = false)              // matches "name TEXT NOT NULL"
    private String name;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "user_id", nullable = false)     // matches "user_id INT NOT NULL REFERENCES users(id)"
    private User user;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "program_id", nullable = true)   // matches "program_id INT NULL REFERENCES programs(id)"
    private Program program;
```

So each annotation is declaring, in Java, a fact that's *also* written in the
SQL DDL — that's exactly the trap that got hit: nothing keeps these two
declarations in sync automatically. Editing `V1__init.sql` to add `name`,
and separately editing `Workout.java` to add the `name` field, are two
independent edits that happen to agree here — but Hibernate has no way to
know you *also* need to run that SQL against the live database.
`ddl-auto=validate` only checks "does the live table match what the
annotations claim" at startup and fails loudly if not.

`ON DELETE CASCADE` / `ON DELETE SET NULL` have **no JPA annotation
equivalent** — those are pure DB behavior (what Postgres does when the
referenced row is deleted), invisible to Hibernate entirely. If a `User` row
is deleted directly in the DB, Postgres cascades it per the FK; Hibernate
never even hears about it unless it deleted the row itself.

## Same relationship, `householdPlanner` style

Compare to `GroceryList` — no ORM at all:

```sql
CREATE TABLE grocery_lists (
    id INT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name TEXT NOT NULL DEFAULT '',
    household_id INT NOT NULL REFERENCES households(id)
);
```

```go
type GroceryList struct {
    ID          int
    Name        string
    HouseholdID int
}
```

```go
sql := `SELECT id, name, household_id FROM grocery_lists WHERE household_id = $1;`
rows, err := r.db.Query(ctx, sql, hid)
...
err := rows.Scan(&g.ID, &g.Name, &g.HouseholdID)
```

There's no declared mapping at all — the struct field order and the
`SELECT` column order just have to line up *by hand*, positionally, in every
single query. Nothing checks this at compile time or startup; if the
`SELECT` columns are reordered without reordering the `Scan()` args, `Name`
silently gets scanned into `ID`. JPA's annotations exist precisely to
centralize that mapping once, in one place, instead of repeating (and
risking a mismatch) in every query — the cost is the exact bug above, where
the "one place" and the real database can drift apart if the migration
never actually gets run.

## Net comparison

`pgx`/raw SQL never has a schema-validation step to fail (there's no
`ddl-auto=validate` equivalent) — if `grocery_lists` were missing a column,
that would only surface at runtime when a specific query hits it, not at
startup for the whole app. JPA fails faster and louder (which is what just
happened), at the cost of a layer of mapping annotations that has to be kept
honest against the schema by hand.

## Full annotation catalog (every one actually used in this project)

Grepped across `User`, `Program`, `Workout`, `Exercise`, `ProgramDay`:
`@Entity`, `@Table`, `@Id`, `@GeneratedValue`, `@Column`, `@ManyToOne`,
`@OneToMany`, `@JoinColumn`, `@UniqueConstraint`, plus Lombok's `@Getter`/
`@Setter` (not JPA — see the callout at the end).

### `@Entity`

Goes on the class. Tells Hibernate "this class is persistable — track an
instance of it as a row somewhere." No parameters used in this project.
Without it, none of the other annotations matter — `@Table`, `@Id`, etc. on
a non-`@Entity` class are just inert metadata Hibernate never looks at.

### `@Table(name = "...", uniqueConstraints = ...)`

Goes on the class, optional. Picks which physical table the entity maps to.

- `name = "workouts"` — without this, Hibernate derives a table name from
  the class name via its naming strategy (Spring Boot's default lowercases
  and snake_cases it, so `Workout` → `workout`, not `workouts`) — which is
  exactly why every entity here needs an explicit `name`, since the tables
  are plural.
- `uniqueConstraints = @UniqueConstraint(columnNames = {"program_id", "day_order"})`
  (on `ProgramDay`) — declares a composite `UNIQUE` constraint spanning two
  columns, matching `V1__init.sql`'s `UNIQUE (program_id, day_order)`. This
  is a real DDL-level fact Hibernate would generate if it were creating the
  schema — but since `ddl-auto=validate` never creates anything here, this
  annotation is purely documentation unless the SQL migration also declares
  it (it does). `@UniqueConstraint` only exists nested inside `@Table` (or
  `@JoinTable`) — never on its own.

### `@Id`

Goes on a field. Marks it as the entity's primary key — the value Hibernate
uses to tell rows apart, to decide `INSERT` vs `UPDATE` in `repo.save(...)`,
and what `findById(...)` looks up by. Every `@Entity` needs exactly one (or
a composite key via `@EmbeddedId`/`@IdClass`, not used here).

### `@GeneratedValue(strategy = GenerationType.IDENTITY)`

Goes on the `@Id` field. Says the database generates the value, not Java —
matching `id INT GENERATED BY DEFAULT AS IDENTITY` in the SQL. Practical
effect: when you `new Workout(...)`, `id` is `null`; only after
`repo.save(...)` actually executes the `INSERT` does Hibernate read back
whatever Postgres assigned and populate the Java field. `IDENTITY`
specifically means "one row inserted per `save()` immediately" — Hibernate
can't batch inserts under this strategy, unlike `GenerationType.SEQUENCE`
(not used here), which reserves ids up front and can batch. Irrelevant at
this project's scale, but it's the reason `IDENTITY` isn't always the
default recommendation for high-throughput inserts.

### `@Column(nullable = ..., unique = ..., columnDefinition = "...")`

Goes on a plain (non-relationship) field. Declares constraints on the
mapped column — all three parameters appear in this project:

- `nullable = false` / `nullable = true` — matches `NOT NULL` / nothing in
  the SQL. `nullable = true` is actually the JPA *default* for `@Column`
  when omitted, so writing it out (as `Exercise.note` and `Program.deloadInterval`
  do) is purely for-the-reader clarity, not functionally required.
- `unique = true` (`User.username`) — matches `username TEXT UNIQUE NOT NULL`.
  Same caveat as `@UniqueConstraint`: real DDL fact, but only actually
  enforced because the SQL migration separately declares it too, since
  `ddl-auto=validate` doesn't create constraints, only checks them.
- `columnDefinition = "BOOLEAN DEFAULT FALSE"` (`Program.active`, etc.) — an
  escape hatch that hands Hibernate a literal fragment of DDL for this
  column instead of it inferring one. It only matters if Hibernate were
  generating the schema (`ddl-auto=create`/`update`); under `validate`,
  Hibernate never reads this back out to compare against the live column's
  actual default, so right now it's inert documentation of what the
  migration *should* say (and does: `active BOOLEAN DEFAULT FALSE`) rather
  than something enforced by JPA at runtime.

A field with no `@Column` at all (there aren't any in this project, but
it's worth knowing) still gets persisted — Hibernate maps every field of an
`@Entity` by default, deriving a column name from the field name. `@Column`
only needed when a constraint or a non-default column name is being
declared.

### `@ManyToOne(fetch = ...)` + `@JoinColumn(name = ..., nullable = ...)`

Always appear together in this project. `@ManyToOne` declares the
relationship's *multiplicity* (many rows on this side can reference the
same row on the other side — see the earlier `@ManyToOne` vs `@OneToOne`
discussion). `@JoinColumn` says which actual FK column holds it:

- `name = "user_id"` — the column name, matching the SQL.
- `nullable = false` / `nullable = true` — same meaning as on `@Column`,
  just describing the FK column specifically (e.g. `Workout.program` is
  `nullable = true` since a workout doesn't have to belong to a program).
- `fetch = FetchType.LAZY` — every `@ManyToOne` here overrides JPA's own
  default, which is actually `EAGER` for `@ManyToOne`/`@OneToOne` (only
  `@OneToMany`/`@ManyToMany` default to `LAZY`). `LAZY` means Hibernate
  doesn't `SELECT` the related row until code actually calls the getter
  (`workout.getUser()`) — it hands back a runtime-generated proxy subclass
  until then. Flagged earlier: this only currently "works" from Thymeleaf
  templates because Spring Boot's Open-in-View setting keeps the DB session
  open through view rendering — outside that, accessing a lazy field after
  the request/transaction ends throws `LazyInitializationException`.

### `@OneToMany(mappedBy = "...", fetch = ...)`

The *inverse* side of a `@ManyToOne` — declared on `Workout.exercises`,
pointing back at `Exercise.workout`. `mappedBy = "workout"` is the important
part: it says "don't create a new FK column for this side, the relationship
is already owned by the `workout` field over on `Exercise`— I'm just a
read-only navigation back to it." Get this string wrong (a typo, or a
renamed field on the other side not updated here) and Hibernate throws a
startup error, since it can't find a field by that name on `Exercise`.

Without `mappedBy`, `@OneToMany` would assume *this* side owns the
relationship and try to create its own join table — which is the
`@ManyToMany`-shaped mistake from earlier in this conversation, just for
`@OneToMany` instead. `fetch = FetchType.LAZY` here is actually the JPA
default for `@OneToMany` already (unlike `@ManyToOne`), so it's redundant —
written for consistency with the rest of the file rather than necessity.

### Not JPA at all: Lombok's `@Getter` / `@Setter`

These come from `lombok`, not `jakarta.persistence` — a completely separate
library that generates boilerplate getter/setter methods at compile time so
they don't have to be hand-written. Hibernate happens to need public
getters/setters (or field access, depending on where `@Id` is placed) to
read and write entity state, so Lombok and JPA end up looking like they
cooperate, but neither library knows the other exists. Notice `User` only
has `@Getter` at the class level, with `@Setter` placed on just the
`username` field alone — meaning `id` and `pwd` get no setter generated at
all (`id` shouldn't be settable — it's DB-generated; `pwd` presumably
pending whatever the hand-rolled auth work ends up needing).
